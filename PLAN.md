## 1. Stack and why

| Layer | Choice | Reason |
|---|---|---|
| Web framework | FastAPI | Fast to build, typed, automatic OpenAPI (helps the API First bonus) |
| Templates | Jinja2, server-rendered | No separate frontend build, works offline, easy to explain |
| Interactivity | htmx (file vendored into `static/`, never a CDN) | Partial updates without a JS framework |
| ORM | SQLAlchemy 2.0 | Standard, defendable |
| Migrations | Alembic | Migration path = Adoptability score |
| DB | PostgreSQL 16 | You know it; the data is relational |
| Passwords | argon2 (argon2-cffi) | Current best practice |
| Sessions | Server-side sessions table, random token in an HttpOnly cookie | Revocable, easy for the checker (fixed seeded tokens) |
| Tests | pytest + FastAPI TestClient against a test Postgres | Real DB, same as production |

**Repo:** https://github.com/PawanBhandari03/DogFood-HackaThon (created with the MIT LICENSE only; clone it into this folder at kickoff).

**Ports:** the app is on host port 8080 (free). The Postgres container is **not published to the host**, because host ports 5432/5433 are already taken by the user's other projects (blog-db, backend-db). The app reaches the db over the compose network.

**Offline rule:** there are no CDNs anywhere. Fonts, htmx and CSS all live in `src/app/static/`.
**Open risk:** `docker compose up` must build the image (a pip install needs the network the first time). Mitigations: pin the base images, and consider vendoring wheels into `vendor/wheels/` so the build itself is offline. **Ask in Discord** whether a judge's first build may use the network.

## 3. Data model (tables)

|---|---|---|
| `users` | id, email (unique, lower-cased), name, password_hash, is_admin, created_at | One account per email |
| `sessions` | token_hash, user_id, created_at, expires_at, user_agent | We store only a hash of the token |
| `events` | id, external_id, slug, name, description, starts_at, submissions_close_at, judging_close_at, voting_open_at, voting_close_at, results_published_at | All timestamps UTC |
| `event_roles` | user_id, event_id, role (`organizer` / `judge` / `participant`) | Roles are **per event**; admin is global |
| `tracks` | id, event_id, external_id, name | |
| `prizes` | id, event_id, track_id (nullable), name, description, rank | |
| `judge_tracks` | user_id, event_id, track_id | Which tracks a judge covers |
| `teams` | id, event_id, external_id, name, invite_code (random, rotatable) | **Names are NOT unique**: the fixture has 3× "StillTrail" and 2× "OpenSignal" / "AmberSwitch" |
| `team_members` | team_id, user_id, is_lead | Unique (event, user): one team per person per event |
| `projects` | id, event_id, team_id, track_id, external_id, title, summary, repo_url, status (`draft`/`submitted`/`withdrawn`), submitted_at, updated_at, duplicate_of (nullable FK) | |
| `rubric_criteria` | id, event_id, key, label, weight, min_value, max_value, position | Fixture: functionality / quality / innovation |
| `assignments` | id, judge_user_id, project_id, status (`pending`/`done`), assigned_at, conflict_flag | Unique (judge, project) |
| `scores` | id, assignment_id (unique), comment, submitted_at | One score sheet per assignment |
| `score_values` | score_id, criterion_id, value | Check constraint: value between min and max |
| `audit_log` | id, at, actor_user_id, event_id, action, entity_type, entity_id, before (jsonb), after (jsonb), ip | Append-only, readable by organizers |
| T3: `votes`, `comments`, `vote_tokens` | | Later |

**Fixture import rules**
- Event `submissions_close_at` = fixture `2026-03-01T18:00:00Z`, **unchanged**, so the event is honestly closed and the checker's late POST is refused.
- Every judge email becomes a user with the `judge` role plus their `judge_tracks`.
- Every team member email becomes a user with the `participant` role and joins the team.
- Every fixture score creates an `assignment(status=done)` plus a `score`.
- To represent the "unfinished batches", top every project up to **3 assignments** with `pending` ones (track-matched, least-loaded). Projects that have fewer than 3 done reviews then show as incomplete in the progress dashboard.

## 5. Roles and isolation (the 25% criterion)

- **One place decides access:** FastAPI dependencies in `auth/` (`current_user`, `require_event_role(role)`), plus **query scoping**. Judge queries always filter `WHERE assignment.judge_user_id = me`. Nothing is hidden only in templates.
- Rules:
  - Visitor: public gallery, event pages, published results.
  - Participant: their team, their project (draft/edit until the deadline).
  - Judge: only their assigned projects and **only their own scores**. They can't see other judges' scores or the aggregate until results are published.
  - Organizer: everything in their event: assignment, progress, raw and normalized results, CSV, audit log.
  - Admin: users and events, across the whole instance.
- `/api/judges/{judge_id}/scores` → **403** unless `judge_id` is the caller (or the caller is an organizer of that event).
- **Deadline enforcement:** a single `services/deadline.py` check runs **first** in every create/edit/submit path. After close → **403 `submissions_closed`**, even before body validation, so the refusal is for the real reason. Tested against an open event too, so we know it isn't a coincidental 4xx.
- Every state change writes an `audit_log` row (who, what, before/after).

## 6. Scoring and normalization (JUDGING.md + bonus)

**Weighted raw score** per score sheet = Σ(weight × value) / Σ(weight). The organizer edits the weights on the rubric page (default equal).

**Normalization: per-judge z-score with shrinkage** (empirical-Bayes style), written up with the fixture's before/after numbers:
1. For each judge j with n_j score sheets: mean m_j, standard deviation s_j of their weighted scores.
2. Global mean M and global sd S across all sheets.
3. Shrink toward the global values, with a prior strength k (default 3):
   - m̂_j = (n_j·m_j + k·M) / (n_j + k)
   - ŝ_j = sqrt((n_j·s_j² + k·S²) / (n_j + k))
4. Normalized sheet score z = (x − m̂_j) / ŝ_j, mapped back to the rubric scale: M + z·S.
5. Project score = mean of the normalized sheets. Also show the review count and a simple uncertainty (standard error) so an organizer sees that a 2-review project is less certain.

Why this is defensible:
- It removes harsh/generous offsets and different score spreads.
- Shrinkage stops a judge with 1–2 scores from being wildly "corrected".
- A zero-spread judge (all identical scores) gets ŝ_j > 0 from the prior, so there's no division by zero and their sheets land near the middle. Their scores carry little ranking information, which is correct.

The organizer can switch between **Raw / Normalized** on the results page. Both appear in the CSV.

**Bonus (Normalization Proof):** a page plus a JUDGING.md section showing, on the fixture data, per-judge offsets, the ranking before vs after, and which projects moved and why. Also a unit test on a synthetic case (a judge who is +1 harsher on everything → after normalization, the ranking matches the unbiased judge's).

**Assignment algorithm** (T2): for each project needing reviews, choose judges who (a) cover the project's track, (b) aren't team members, (c) aren't already assigned, (d) have the fewest current assignments. Ties are broken randomly with a stored seed, so a run is reproducible. It's configurable with k reviews per project (default 3). The organizer can run it (batch) or assign manually.

## 8. Design direction ("not the usual AI look")

Theme: **the hackathon as a printed newspaper / broadsheet.** Events are "editions", projects are "articles", results are the "front page".

- **Fonts** (all OFL, self-hosted woff2):
  - Display: **Fraunces** (soft, quirky serif; use its large optical size for headlines)
  - Body/UI: **Atkinson Hyperlegible** (very readable, rarely used, good accessibility)
  - Numbers/data/meta: **Martian Mono** (scores, timestamps, ids)
- **Palette:** paper `#F3EEE3`, ink `#1A1A18`, rule lines `#1A1A18` at 15–100%, accent **vermilion** `#D2461E`, secondary **bottle green** `#1E4A38`, a highlight "marker yellow" `#F2D64B` used very sparingly. Dark mode: charcoal paper `#16150F` with warm off-white ink.
- **Layout:** a strict 12-column grid, hairline rules between columns, a masthead with the event name set big, a dateline strip (time left until the deadline in mono), and project cards as "article columns" with a kicker (track) above the title.
- **Details:** rubber-stamp status badges (DRAFT / SUBMITTED / CLOSED / DUPLICATE?) slightly rotated; scores shown as big mono numerals; a ranked results page styled like a sports-results table. No gradients, no rounded pill buttons, no purple, no emoji icons. Square corners, 2px ink borders, underlined links.
- Mobile: single column, same rules and type scale.
